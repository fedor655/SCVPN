# SCVPN для macOS — версия на Swift

Нативный клиент: SwiftUI-приложение и привилегированный демон, оба на Swift, без
единой внешней зависимости. Заменяет Python/PySide6-версию из `../MacOS/`,
сохраняя все форматы данных и весь протокол сокета без изменений.

Собранный бандл — **2,6 МБ** против **223 МБ** у Python-версии.

## Сборка и запуск

```bash
./build.sh && open dist/SCVPN.app
```

`swift run` для приложения **не работает и не должен**: SwiftUI из SPM-таргета
обязан запускаться из собранного бандла, иначе `Bundle.main` укажет на `.build`,
не подхватится `Info.plist` с `NSCameraUsageDescription`, и приложение получит
не ту activation policy. Для демона и проверок `swift build` / `swift test`
работают как обычно.

Требуется Apple Silicon: сборка на Intel обрывается с ошибкой. Минимальная
система — macOS 13.0.

## Интерфейс

Экран — кнопка подключения, статус и список серверов. Всё остальное в меню «⋯»:

| Пункт | Что делает |
|---|---|
| Способ подключения | системный прокси или TUN (весь трафик, нужен root) |
| Отпечаток TLS | авто-подбор или конкретный |
| Сетевой стек TUN | gvisor / system / mixed — крутить, если туннель странно себя ведёт |
| Включать системный прокси | только для режима «прокси» |
| Блокировать рекламу | правило в конфиге Xray |
| Раздельное туннелирование… | маршрутизация целиком: всё через VPN, обход, или какие приложения идут в туннель (нужен TUN; выбор приложений на macOS живьём не проверен) |
| Подписки… | список подписок, ссылка, QR-код, удаление подписки целиком |
| Измерить пинг | TCP-пинг всех серверов |
| Скачать ядро Xray | разовая загрузка ядра и гео-баз |
| Скачать компоненты TUN | попросить системный компонент скачать `sing-box` |
| Удалить компоненты TUN… | виден, только когда есть что удалять |
| Удалить системный компонент… | снять привилегированный демон |
| Показывать лог ядра | панель с выводом Xray внизу окна |

Полосы заголовка у окна нет: содержимое заведено под неё, светофор опущен в
центр шапки, окно тащится за шапку.

## Как устроен TUN и почему так

TUN на macOS требует root. Можно было бы спрашивать пароль на каждое
подключение, но тогда остаётся дыра, из-за которой такие клиенты и славятся
нестабильностью: приложение упало или его сняли, а `sing-box` работает от root
и держит маршруты. Весь трафик системы уходит в мёртвый туннель, и выглядит это
как «интернет пропал». Прибить `sing-box` может только root, то есть нужен ещё
один диалог пароля — а показать его уже некому.

Поэтому приложение держит открытое соединение с демоном всё время работы.
Оборвалось соединение — значит приложение мертво — демон сам сносит `sing-box`
и возвращает маршруты. Не при следующем запуске, а сразу.

### Отличия от Python-версии

**Демон ставится через `SMAppService`**, а не `osascript` + `launchctl
bootstrap`. Plist едет внутри бандла, в
`Contents/Library/LaunchDaemons/com.scvpn.helper.plist`.

Следствия:

- `/Library/LaunchDaemons/com.scvpn.helper.plist` больше не создаётся;
- `/Library/Application Support/SCVPN/code` не нужен вовсе — код демона внутри
  бандла, копировать его никуда не надо;
- **первый `register()` штатно возвращает ошибку** `code=1` и переводит службу в
  `requiresApproval`. Это не сбой, а шаг сценария: система plist приняла, ей
  нужно согласие пользователя в System Settings → General → Login Items;
- снять компонент вручную — там же, в Login Items.

**Подмена бандла на месте службу не обновляет.** Проверено (Фаза 0, Задачи 0.2 и
0.3): ни новый бинарник, ни изменённый plist не подхватываются, а служба
перестаёт подниматься вовсе. Поэтому приложение хранит `helper_version` в
`settings.json` и при несовпадении делает `unregister()` + `register()`. Это
условие корректности, а не оптимизация: `ExitTimeOut = 40` — расчёт худшего
случая снятия, и служба со старым значением получит SIGKILL на середине снятия.

**Ограничения по расположению бандла нет.** Проверено живьём из `/Applications`,
`~/Applications`, `/Users/Shared` и `~/Downloads` — везде регистрация проходит и
демон поднимается от root. TCC-баг Python-версии не воспроизводится: он был
свойством способа запуска (launchd вёл абсолютный путь к интерпретатору внутрь
пользовательской папки), а не папки.

## Структура

| Файл | За что отвечает |
|------|-----------------|
| `Sources/SCVPNCore/` | вся логика: модели, парсеры, конфиги, хранилище, клиент демона |
| `Sources/SCVPNCore/SingboxConfig/` | конфиг sing-box и валидация недоверенного ввода |
| `Sources/SCVPNCore/HelperClient.swift`, `Tun.swift` | клиент демона: поднять и снять туннель |
| `Sources/SCVPNCore/SystemProxy.swift` | системный прокси через `networksetup`, со снимком для отката |
| `Sources/SCVPNCore/HelperInstaller.swift` | регистрация демона через `SMAppService` |
| `Sources/SCVPNHelperKit/` | логика демона: сокет, надзор за sing-box, установка sing-box |
| `Sources/SCVPNHelper/main.swift` | точка входа демона, десяток строк |
| `Sources/SCVPNApp/` | SwiftUI: окно, меню, диалоги |
| `Tools/smprobe/` | зонд `SMAppService` для Фазы 0 плана переписывания |
| `Tools/install-helper-dev.sh` | ручная установка демона на время Фазы 2 |

Логика демона живёт в `SCVPNHelperKit`, а не в исполняемом таргете, потому что
SwiftPM не даёт тестовому таргету линковать executable. Ровно по той же причине
платформенный слой приложения лежит в `SCVPNCore`, а не в `SCVPNApp`.

## Проверка

```bash
swift test                          # всё
swift test --filter DeadMansSwitch  # одна группа
```

Три проверки трогают систему по-настоящему, и это осознанно:

- `SystemProxyLiveTests` включает и выключает системный прокси на этой машине —
  молча сломанный откат оставляет без интернета, и ловить это надо здесь.
  Пропускается, если на машине уже стоит **чужой** прокси: падение посреди
  проверки затёрло бы его настройку.
- `SignalTests` поднимает демона отдельным процессом и шлёт ему сигналы.
- `RealProfilesTests` читает настоящий `../MacOS/data/profiles.json`, если он
  есть, и прогоняет через круг чтение-запись. Файла нет — `XCTSkip`, а не
  зелёный молчком.

### Ручная проверка TUN и dead-man's switch

Полный сценарий — в `../MacOS/README.md`, он не изменился. Единственная поправка:
`pgrep -f "run.py --helper"` заменяется на `pgrep -f scvpn-helper`.

Главное — шаг 4: при поднятом туннеле убить приложение `kill -9` и убедиться,
что **PID демона остался тем же**. Сменился — значит демон тоже погиб, его поднял
launchd, а новый демон подметает сироту сам, и проверка позеленеет при полностью
сломанном обнаружении обрыва.

Делать это не по SSH в ту же машину: провальный исход означает трафик, запертый
в мёртвом туннеле.
