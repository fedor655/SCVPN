# План переноса Windows-версии на C# (WPF, .NET)

Дата составления: 16.08.2026.

> **Состояние: код написан, на Windows ещё не собирался.** Что сделано,
> что проверено и чем это отличается от плана — в разделе 18 внизу.

Цель: заменить нынешнее приложение на Python + PySide6 (`desktop/Windows/`,
5372 строки) нативным приложением на C#, сохранив функциональность один в один,
данные пользователя — без миграции, а установку — обновлением поверх старой.

---

## 1. Решения, принятые до начала

| Вопрос | Решение |
|---|---|
| UI-стек | WPF |
| Минимальная ОС | Windows 10 21H2 (сборка 19044) и новее |
| Среда разработки | Parallels Desktop с Windows on ARM |
| Объём | паритет 1:1, после приёмки Python-версия удаляется |

Решения, принятые по умолчанию (скажи, если нужно иначе, — они дёшево меняются
только сейчас, до первого коммита):

* **.NET 10 (LTS).** У .NET 8 поддержка кончается в ноябре 2026 — начинать на
  ней новый проект бессмысленно. TFM: `net10.0-windows10.0.19041.0`,
  `SupportedOSPlatformVersion=10.0.19041.0`. Такой TFM даёт доступ к WinRT-API
  (нужен камере в сканере QR) и при этом ставит нижнюю планку ниже выбранной
  21H2, так что ограничение задаётся установщиком, а не компилятором.
* **Self-contained-публикация.** У пользователя не должно быть требования
  «сначала поставьте .NET Desktop Runtime». Папка выходит примерно 150 МБ —
  ровно того же порядка, что нынешняя сборка PyInstaller с PySide6, то есть
  регресса нет. Trimming для WPF не поддерживается, поэтому уменьшать размер
  нечем и пытаться не нужно.
* **Установщик остаётся Inno Setup**, тот же `installer.iss` с тем же `AppId`.
  MSIX не берём: он требует подписи, ломает привычный путь установки и ничего
  не даёт приложению, которому и так нужны права администратора.
* **Пакеты NuGet — только три:** `CommunityToolkit.Mvvm`, `QRCoder` (генерация
  QR), `ZXing.Net` (распознавание QR). Всё остальное — стандартная библиотека.
  Она закрывает HTTP, JSON, ZIP, реестр, процессы, сокеты, криптографию —
  то есть все пять сторонних зависимостей нынешнего `requirements.txt`.
* **Папка разработки — `desktop/Windows-cs/`.** По приёмке: `git rm -r
  desktop/Windows && git mv desktop/Windows-cs desktop/Windows`. Так вся
  история порта видна отдельно, а рабочая Python-версия до последнего дня
  остаётся собираемой и запускаемой — она нужна как эталон (см. раздел 3).

## 3. Ключевой рычаг: core-swift уже сделал половину работы

В репозитории лежит `core-swift/` — та же логика, уже переведённая с Python на
строго типизированный язык, с 22 файлами тестов (2416 строк). Это меняет
подход к порту:

**Переводим на C# не Python, а Swift.** Все решения, которые в Python
принимаются словарями и утиной типизацией (что делать с неизвестным полем
`extra`, как хранить настройки со смешанными типами, как разбирать `ss://` с
base64 внутри userinfo), в `core-swift` уже приняты в пользу статических типов —
и приняты один раз, вместе с тестами, которые их фиксируют. В C# они переносятся
почти дословно:

| core-swift | C# |
|---|---|
| `Codable` + `CodingKeys` | `System.Text.Json` + `[JsonPropertyName]` |
| `JSONValue.swift` (произвольный JSON) | `JsonElement` / `JsonNode` |
| `enum SplitMode` | `enum SplitMode` |
| `Result` / `throws` | исключения + `TryParse`-пары |
| XCTest | xUnit |

Особенно ценны `Storage/JSONValue.swift` (как хранить настройки, где значения
разных типов и есть неизвестные ключи) и `Parsing/Base64.swift` (панели шлют
base64 то с набивкой, то без, то в URL-безопасном алфавите — `Convert.FromBase64String`
строгий и на этом падает).

Где Python и Swift расходятся — **правым считается Swift**: он новее и покрыт
тестами. Расхождения выписывать в отдельный список по ходу работы, в конце
пройтись по нему и решить каждое осознанно.

## 5. Таблица замен

| Сейчас (Python) | Станет (C#) | Примечание |
|---|---|---|
| `requests` | `HttpClient` | один статический экземпляр на приложение |
| `json` | `System.Text.Json` | source-generated контекст, чтобы не мешал будущий trimming |
| `@dataclass` | `class` / `record` | `record` для неизменяемых, `class` для `Server` (мутируется в подборе отпечатка) |
| `winreg` | `Microsoft.Win32.Registry` | `RegistryView.Registry64` вместо `KEY_WOW64_64KEY` |
| `ctypes.windll.Wininet.InternetSetOptionW` | `[DllImport("wininet.dll")]` | один вызов, сигнатура та же |
| `ctypes.windll.shell32.IsUserAnAdmin` | `WindowsPrincipal.IsInRole(WindowsBuiltInRole.Administrator)` | без P/Invoke |
| `ShellExecuteW(..., "runas", ...)` | `ProcessStartInfo { Verb = "runas", UseShellExecute = true }` | отказ от UAC = `Win32Exception.NativeErrorCode == 1223` |
| `subprocess.Popen` | `Process` + `CreateNoWindow = true` | `StandardOutputEncoding = Encoding.UTF8` |
| разбор вывода `tasklist` | `Process.GetProcesses()` | уходит возня с кодировкой cp866; имя без `.exe` — дописать |
| `threading.Thread` + сигналы Qt | `async/await` + `IProgress<T>` | WPF сам маршалит продолжение в UI-поток |
| `QThread` (`ui/workers.py`) | `Task.Run` + `IProgress<string>` | файл исчезает целиком |
| `zipfile` | `System.IO.Compression.ZipArchive` | |
| `socket` TCP-пинг | `TcpClient.ConnectAsync(..., CancellationToken)` | таймаут через токен, а не `settimeout` |
| `hashlib.sha256` | `SHA256.HashData` | |
| `uuid.getnode()` | `NetworkInterface.GetAllNetworkInterfaces()` | запасной путь HWID |
| `platform.machine()` | `RuntimeInformation.OSArchitecture` | **уже учитывает эмуляцию** — весь `arch.py` из ARM-плана не нужен |
| `opencv-python-headless` | WinRT `MediaCapture` + `ZXing.Net` | см. 11.4 |
| `qrcode` | `QRCoder` (только матрица) | рисуем сами, как и сейчас |
| PyInstaller | `dotnet publish` | |

Строка про `RuntimeInformation.OSArchitecture` — самая приятная во всей таблице:
в .NET свойство возвращает архитектуру **операционной системы**, а не процесса,
и на Windows on ARM под эмуляцией честно говорит `Arm64`. Весь модуль `arch.py`
из ARM-плана (шаг 1, `IsWow64Process2` через ctypes) сводится к одному вызову.

## 6. Этап 0 — три спайка, до всякого кода приложения

Полдня. Каждый спайк — отдельный выброшенный проектик, задача — снять
неизвестность, а не написать код, который останется.

### 0.1. Кросс-сборка x64 с arm64-хоста

Машина разработки — Windows on ARM, а основная аудитория на x64. Проверить:

```powershell
dotnet publish -c Release -r win-x64   --self-contained -p:PublishReadyToRun=true
dotnet publish -c Release -r win-arm64 --self-contained -p:PublishReadyToRun=true
```

Собрать пустое WPF-окно и опубликовать обе цели с arm64-машины. ReadyToRun
компилирует IL в машинный код заранее, и кросс-компиляция x64 с arm64-хоста —
самое вероятное место отказа. Если `crossgen2` для x64 не поедет: либо выключить
`PublishReadyToRun` для x64 (потеряется скорость холодного старта, не более),
либо собирать x64 в GitHub Actions на `windows-latest`. Решение принять здесь и
записать, а не выяснять на этапе 5, когда до релиза останется день.

**Готово, когда:** обе папки собраны, x64-сборка запускается в этой же
ARM-виртуалке (под эмуляцией), arm64-сборка — нативно.

### 0.2. Камера в WPF без OpenCV

Самая хрупкая часть порта. В WPF нет `CaptureElement` из UWP, поэтому нужен один
из двух путей:

* **`MediaFrameReader`** — поток кадров, каждый кадр `SoftwareBitmap`, из него
  `WriteableBitmap` для показа и массив яркости для `ZXing.Net`. Плавно,
  примерно 60 строк, но API многословный и любит отвалиться на конкретных
  камерах;
* **периодический `CapturePhotoToStreamAsync`** раз в 300–400 мс — примитивно,
  строк двадцать, но у части камер даёт щелчок затвора и заметный лаг.

Проверить оба на камере, проброшенной в Parallels. Записать, какой выбран, и
почему. Если не поедет ни один — запасной вариант в 15.3.

**Готово, когда:** окно показывает картинку с камеры и печатает в консоль
содержимое поднесённого QR.

### 0.3. Job-объект против осиротевших ядер

Проверить, что `xray.exe` и `sing-box.exe`, назначенные в job-объект с флагом
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, умирают вместе с приложением, если его
снять из диспетчера задач. Если да — 120 строк `cleanup_stray()` из `tun.py`
превращаются в 30 строк `ProcessJob.cs`, и главный класс аварий («туннель поднят,
управлять нечем») закрывается ядром ОС, а не нашей уборкой при следующем старте.

**Готово, когда:** приложение снято через «Снять задачу», оба дочерних процесса
исчезли, `ipconfig` не показывает адаптер `SCVPNTun`.

## 7. Этап 1 — `Core/`: логика без интерфейса

Полтора-два дня. Порядок именно такой: сначала то, что проверяется тестами без
Windows, без сети и без ядра.

### 7.1. `Server.cs`

Перевод `models.py` + `core-swift/Models/Server.swift`. Поля те же и с теми же
именами в JSON — файл `profiles.json` обязан читаться и писаться байт в байт
совместимо:

```csharp
public sealed class Server
{
    [JsonPropertyName("protocol")] public string Protocol { get; set; } = "vless";
    [JsonPropertyName("alter_id")] public int AlterId { get; set; }
    [JsonPropertyName("ws_path")]  public string WsPath { get; set; } = "/";
    [JsonPropertyName("public_key")] public string PublicKey { get; set; } = "";
    // …и так все поля со snake_case-именами
    [JsonPropertyName("extra")] public Dictionary<string, JsonElement> Extra { get; set; } = new();
}
```

Так как `to_dict()` в Python пишет `self.__dict__` целиком, снимок полей нужно
сверить построчно — пропущенное поле не сломает загрузку, а тихо потеряет
настройку сервера при первом же сохранении профилей.

`to_outbound()` → `ToOutbound(string tag)`, возвращает `JsonObject`.
`key()` → `Key()`, формат строки менять нельзя: по нему отсеиваются дубликаты
при обновлении подписки и хранится `selected_key` в настройках.

### 7.2. `LinkParser.cs`

Перевод `subscription.py` (разбор ссылок) и `core-swift/Parsing/LinkParser.swift`.
Четыре протокола, у каждого свой формат:

* `vless://uuid@host:port?params#name` — обычный URI;
* `vmess://<base64 JSON>` — внутри JSON с однобуквенными ключами (`add`, `aid`,
  `net`, `tls`, `sni`);
* `trojan://password@host:port?params#name`;
* `ss://<base64 method:password>@host:port#name` — а бывает и целиком в base64.

Отдельно `Base64Url.cs`: набивка `=` часто отсутствует, алфавит бывает
URL-безопасный. `Convert.FromBase64String` на таком падает — нужна обёртка,
готовая лежит в `core-swift/Parsing/Base64.swift`.

### 7.3. `XrayConfigBuilder.cs` и `SingboxConfigBuilder.cs`

Перевод `xray_config.py` и `build_singbox_config()` из `tun.py`. Собирают
`JsonObject`. Порядок ключей внутри объектов значения не имеет для ядра, но
имеет для эталонных тестов — сравнивать нужно разобранные документы, а не строки
(см. 13.2).

### 7.4. `Store.cs`

`profiles.json` — типизированная модель. `settings.json` — сложнее: это словарь
со значениями разных типов, и в нём лежат ключи, которых C#-версия может не
знать (`tun_stack` относится к macOS, `hwid` записан один раз навсегда). Терять
неизвестные ключи нельзя. Решение:

```csharp
public sealed class Settings
{
    [JsonPropertyName("socks_port")] public int SocksPort { get; set; } = 10808;
    // …известные ключи…
    [JsonExtensionData] public Dictionary<string, JsonElement> Unknown { get; set; } = new();
}
```

`JsonExtensionData` сохраняет всё незнакомое при обратной сериализации. Без него
первый же запуск C#-версии стёр бы `hwid`, и у каждого пользователя занялся бы
новый слот в лимите устройств панели — ровно та беда, о которой предупреждает
комментарий в `hwid.py`.

Писать настройки **атомарно**: во временный файл рядом, затем
`File.Move(tmp, target, overwrite: true)`. Нынешний Python пишет напрямую, и
выключение питания в этот момент оставляет пустой `settings.json` — с потерей
того же `hwid`. Раз всё равно переписываем, чинится бесплатно.

### 7.5. `SubscriptionInfo.cs`, `SubscriptionFetcher.cs`

Перевод `subinfo.py`. Внимание к одной детали: заголовок `content-disposition` в
`HttpClient` лежит не в `response.Headers`, а в `response.Content.Headers` —
частая ошибка, и приводит она к пустому имени аккаунта в экране подписки.

Заголовки запроса: `User-Agent` (`v2rayNG/1.9.5`) плюс четыре заголовка
устройства из `Hwid`. Без них панели с привязкой к устройствам отдают заглушку
вместо серверов.

Текст ошибки при недоступном домене подписки (`SubscriptionError` в
`subscription.py`) перенести дословно — он объясняет замкнутый круг
«подписку не обновить без VPN» и стоил, судя по комментарию, отдельной итерации
поддержки.

### 7.6. `TcpPing.cs`, `FingerprintProbe.cs`, `XrayRunner.cs`

`XrayRunner` — запуск `xray.exe`, чтение stdout построчно в `async`-цикле:

```csharp
_proc = Process.Start(new ProcessStartInfo(exe, $"run -c \"{cfgPath}\"")
{
    WorkingDirectory = Paths.BinDir,      // рядом лежат гео-базы
    RedirectStandardOutput = true,
    RedirectStandardError  = true,
    StandardOutputEncoding = Encoding.UTF8,
    CreateNoWindow = true,
    UseShellExecute = false,
});
_job.Assign(_proc);                        // см. 0.3
```

`FingerprintProbe` (перевод `connect.py`) поднимает временное ядро и ходит через
его HTTP-вход:

```csharp
var handler = new HttpClientHandler { Proxy = new WebProxy($"http://127.0.0.1:{httpPort}"), UseProxy = true };
```

Порядок перебора отпечатков (`firefox, chrome, safari, edge, ios, randomized`)
и адреса проб (`api.ipify.org`, `gstatic.com/generate_204`) не менять: числа
пинга должны оставаться сравнимыми с Android- и macOS-версиями.

**Готово, когда:** `dotnet test` проходит на эталонных файлах из 13.2, а
`Core/` не содержит ни одной ссылки на `System.Windows`.

## 8. Этап 2 — `Native/`: система

День-полтора.

### 8.1. `Paths.cs`

Прямой перевод. Отличие одно: `sys.frozen` в .NET не нужен, режим определяется
проще — но пути обязаны совпасть с текущими:

* данные: `%LOCALAPPDATA%\SCVPN` (`Environment.SpecialFolder.LocalApplicationData`);
* `bin/` рядом с исполняемым файлом (`AppContext.BaseDirectory`);
* имена файлов (`profiles.json`, `settings.json`, `xray_running.json`,
  `singbox_running.json`, `xray.pid`, `singbox.pid`) — прежние.

Отладочный режим («данные в `data/` рядом с проектом») удобно сохранить: пусть
включается по `#if DEBUG` либо по наличию файла-маркера рядом с exe.

### 8.2. `SystemProxy.cs`

`Microsoft.Win32.Registry` для трёх значений в
`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` плюс
P/Invoke `InternetSetOptionW` дважды (39 — `SETTINGS_CHANGED`, 37 — `REFRESH`).
Строка обхода `_BYPASS` — дословно.

Стоит добавить то, чего нет в Python: **сохранять прежнее значение
`ProxyServer`/`ProxyEnable` перед включением и возвращать при выключении**.
Сейчас `disable()` просто гасит флаг, и пользователь с корпоративным прокси
теряет свою настройку молча. `core-swift/SystemProxy.swift` (314 строк) уже
решает эту задачу для macOS — стоит посмотреть, как там оформлено сохранение
прежнего состояния, и повторить логику.

### 8.3. `Hwid.cs` — критично для совместимости

Алгоритм обязан совпасть с Python **до символа**:

1. если `settings.json` уже содержит `hwid` — вернуть его и ничего не считать;
2. иначе: `MachineGuid` из `HKLM\SOFTWARE\Microsoft\Cryptography`
   (`RegistryView.Registry64`);
3. запасной путь — MAC первого сетевого адаптера в формате `mac-%012x`;
4. `SHA256("scvpn-hwid-v1:" + source)`, шестнадцатеричная строка в нижнем
   регистре;
5. форматирование срезами: `[0:8]-[8:12]-[12:16]-[16:20]-[20:32]`.

Обрати внимание на шаг 5: это не настоящий UUID, а именно нарезка первых 32
шестнадцатеричных знаков. Реализовать «правильно» через `Guid` — значит выдать
другое значение и обнулить привязку у всех пользователей.

Заголовки: `x-hwid`, `x-device-os` (`"Windows"`), `x-ver-os`, `x-device-model`
(`Environment.MachineName`). В `x-ver-os` разумно добавить архитектуру — тогда
в панели видно ARM-устройство. Это единственное допустимое изменение в этом
файле; `x-hwid` не трогать ни при каких обстоятельствах.

**Тест обязателен:** на подставленном `MachineGuid` C# должен выдать ту же
строку, что Python. Эталон снять с работающей Python-версии до её удаления.

### 8.4. `Tun.cs` и `ProcessJob.cs`

Самый большой файл системной части. Части:

* **конфиг sing-box** — уже в `Core/SingboxConfigBuilder.cs`;
* **проверка прав** — `WindowsPrincipal`;
* **повышение прав** — `Elevation.cs`, `Verb = "runas"`. Разбор отказа: ловим
  `Win32Exception`, `NativeErrorCode == 1223` (`ERROR_CANCELLED`) означает
  «нажато «Нет» в диалоге UAC» — это самая частая ветка, и текст сообщения
  берём из `_SHELL_EXECUTE_ERRORS[5]` нынешнего кода;
* **запуск и остановка** — как в `XrayRunner`, плюс `WorkingDirectory = bin/`,
  потому что рядом обязан лежать `wintun.dll`;
* **контракт `stop()`** — возвращает `bool`: снят или пережил остановку.
  Не потерять: `main_window` по этому значению решает, имеет ли он право
  показать «Отключено». Комментарий в `tun.py` объясняет, почему это важно —
  перенести его целиком;
* **уборка сирот** — `ProcessJob` закрывает основной случай (см. 0.3), но
  чтение старых `xray.pid` / `singbox.pid` при старте нужно **оставить**: после
  обновления с Python-версии на диске могут лежать её pid-файлы и её процессы.
  Через пару релизов этот код можно будет удалить — пометить комментарием
  `// временно: сироты от Python-версии, убрать после 2 релизов`.

### 8.5. `RunningApps.cs`

`Process.GetProcesses()` вместо разбора `tasklist` в кодировке cp866. Список
скрытых системных процессов `_HIDDEN` — дословно. `ProcessName` в .NET приходит
без расширения, `.exe` дописываем сами — правило sing-box сравнивает с
`process_name`, где расширение есть.

### 8.6. `CoreDownloader.cs`

Перевод `downloader.py` + сразу выбор ассетов по архитектуре (то, что в
ARM-плане было отдельным этапом):

```csharp
static readonly Dictionary<Architecture, string> XrayAsset = new()
{
    [Architecture.X64]   = "Xray-windows-64.zip",
    [Architecture.Arm64] = "Xray-windows-arm64-v8a.zip",
};
```

Плюс то же для суффикса sing-box (`windows-amd64.zip` / `windows-arm64.zip`) и
для пути внутри архива wintun (`amd64/wintun.dll` / `arm64/wintun.dll`).

Метка архитектуры `bin/arch.txt` из ARM-плана (шаг 3) нужна и здесь: без неё
пользователь, поставивший arm64-сборку поверх x64, останется с x64-ядрами и
получит невнятную ошибку запуска. `CorePresent()` и `TunPresent()` сверяют метку
с `RuntimeInformation.OSArchitecture`; несовпадение = «ядра нет», и UI сам
предложит скачать.

Прогресс — `IProgress<(long Got, long Total)>`, отдельно от строк лога, по той
же причине, что описана в комментарии `download_core()`: числа для полоски и
текст для лога — разные вещи.

Поиск ассета Xray делать по префиксу (`name.StartsWith("Xray-windows-arm64")`),
а не по точному совпадению: суффикс `-v8a` в истории проекта уже менялся.

**Готово, когда:** консольная утилита на этом же `Native/` скачивает ядро и
sing-box в `bin/`, `dumpbin /headers bin\xray.exe` показывает нужную машину,
`sing-box check -c` проходит на сгенерированном конфиге.

## 9. Этап 3 — интерфейс: скелет

Два-три дня. Цель этапа — работающее подключение в окне, ещё без диалогов.

### 9.1. Тема

`Theme/Palette.cs` — цвета из `theme.py`, теми же именами. Здесь нужна
осторожность: цвета уже продублированы в трёх местах (`theme.py`,
`android/.../colors.xml`, `core-swift/Theme.swift`), и `ThemeTests.swift`
сверяет Swift с Android. Четвёртая копия без сверки разъедется молча.

**Поэтому:** в `SCVPN.Tests` завести тест, читающий
`android/app/src/main/res/values/colors.xml` из дерева репозитория и
сверяющий каждое значение — ровно как это делает
`core-swift/Tests/SCVPNCoreTests/ThemeTests.swift`. Тест переводится почти
дословно, включая проверку «палитра строго серая» (`R == G == B`).

`Theme/Metrics.cs` — числа из `theme.py` (размеры шапки, кнопки, строк списка,
шкала шрифтов). Комментарии про «те же числа, что в `Style.swift`» перенести:
они единственное, что удерживает три платформы от расползания.

`Theme/Theme.xaml` — `ResourceDictionary` со стилями, значения тянет из
`Palette`/`Metrics` через `x:Static`, чтобы числа жили в одном месте, а не в двух.

Отдельно про шрифты: в Qt разрядка (`letter-spacing`) задавалась через `QFont`,
потому что QSS её не понимает. В WPF это `TextBlock` без встроенной поддержки
трекинга — придётся либо рисовать заголовки через `FormattedText`, либо
расставлять пробелы вручную для трёх мест, где трекинг реально используется
(знак `SCVPN`, заголовки разделов, крупный статус). Мелочь, но всплывёт.

### 9.2. `PowerButton`

Самый заметный элемент окна и самая кропотливая часть UI-порта.
Наследник `ButtonBase`, вся отрисовка в `OnRender(DrawingContext)`:

* шайба — `RadialGradientBrush` с центром `POWER_LIGHT = (0.5, 0.34)` и
  радиусом `0.62`;
* кольцо состояния — `Pen` разной толщины; при ошибке `DashStyle` (пунктир —
  единственный способ различить состояния без цвета);
* бегущая дуга при подключении — `StreamGeometry` с `ArcSegment`, поворот через
  `RotateTransform`;
* «дыхание» в простое — анимация прозрачности.

Здесь WPF заметно лучше Qt: вместо таймеров `POWER_BREATH_FPS = 24` и
`POWER_SPIN_FPS = 60` используются `DoubleAnimation` на собственном
`DependencyProperty` с флагом `AffectsRender`. Композитор сам выберет частоту и
остановит анимацию в свёрнутом окне. Константы FPS из `Metrics.cs` можно не
переносить вовсе — но длительности (`POWER_SPIN = 1.4 с`, `POWER_BREATH = 3.6 с`,
раскрытие дуги `100°`, `POWER_TRACK_OPACITY = 0.22`) обязаны совпасть.

### 9.3. Список серверов

`ListBox` с `ItemTemplate` вместо `QStyledItemDelegate`. Виртуализация в WPF
включена по умолчанию. Метрики: высота строки 52, маркер выделения 2 пикселя,
колонка пинга фиксированные 72 пикселя (иначе правый край значений «гуляет»),
подсветка под курсором — во всю ширину, а не карточкой.

Заголовки разделов (подписки / одиночные серверы) — `GroupStyle` c
`CollectionViewSource`, либо плоский список с элементами-заголовками. Второе
проще и ближе к нынешнему устройству.

`HeadElidedTextBlock`: в WPF `TextTrimming` умеет обрезать только хвост, а в
`_HeadElidedLabel` обрезается **голова** (чтобы у длинного адреса был виден
конец). Готового решения нет — примерно 30 строк с измерением через
`FormattedText`.

### 9.4. Главное окно

Окно обычное, с системной рамкой (нынешнее Qt-окно тоже такое) — значит
`WindowChrome` и кастомный заголовок не нужны. Размер 420×700, минимум 360×540.

Меню «⋯» — `ContextMenu` на `ToggleButton`: `MenuItem` с `IsCheckable` для
флажков и `GroupName` для радиогрупп (отпечаток TLS, режим маршрутизации,
способ подключения). Все пункты и их порядок — по таблице из
`desktop/Windows/README.md`, она же служит списком приёмки.

Оркестровка подключения (`connect_vpn` / `disconnect_vpn`, ~150 строк в
`main_window.py`) переезжает в `MainViewModel` как `async`-методы. Здесь же
уходит `ui/workers.py`: `Worker` → `await Task.Run(...)` с `IProgress<string>`,
`PingWorker` → цикл `await` по серверам с `CancellationToken` (последовательно,
не веером: каждая проба поднимает своё ядро).

**Готово, когда:** в окне виден список серверов из существующего
`profiles.json`, кнопка подключает через системный прокси и через TUN, лог
показывает вывод ядра, пинг меряется.

## 11. Этап 5 — сборка, архитектуры, установщик, миграция

День.

### 11.1. `build.ps1`

Заменяет `build.bat` и `build_installer.bat`. Один параметр — архитектура:

```powershell
param([ValidateSet('x64','arm64','both')] $Arch = 'both')
dotnet publish SCVPN\SCVPN.csproj -c Release -r win-$Arch --self-contained `
    -p:PublishReadyToRun=true -o dist\$Arch
& $ISCC /DMyArch=$Arch setup\installer.iss
```

Версия приложения — в `Directory.Build.props` (`<Version>`), оттуда же
подставляется в `installer.iss` через `/DMyVersion=`. Сейчас версия задана
дважды («0.0.0» в `app_info.py` и в `installer.iss`) и разъедется при первом же
релизе — чинится заодно.

### 11.2. Установщик

Правки к нынешнему `installer.iss`:

```ini
#ifndef MyArch
  #define MyArch "x64"
#endif
ArchitecturesAllowed={#MyArch}compatible
ArchitecturesInstallIn64BitMode={#MyArch}compatible
OutputBaseFilename=SCVPN-Setup-{#MyVersion}-{#MyArch}
Source: "..\dist\{#MyArch}\*"; DestDir: "{app}"; ...
```

`x64compatible` требует Inno Setup 6.3 и новее — проверку версии добавить в
`build.ps1`.

`AppId` **не менять**: тот же идентификатор означает обновление поверх
Python-версии, а не второе приложение в списке программ.

### 11.3. Миграция с Python-версии — обязательный пункт

Установка поверх старой версии по тому же `AppId` **не удаляет** файлы прошлой
установки. В `{app}` останется весь мусор PyInstaller — `_internal\`,
`python3*.dll`, папки PySide6 — сотня мегабайт, которая никогда не подберётся.
Нужен явный блок:

```ini
[InstallDelete]
Type: filesandordirs; Name: "{app}\_internal"
Type: files;          Name: "{app}\python*.dll"
Type: files;          Name: "{app}\Qt6*.dll"
; bin\ НЕ трогаем: там скачанные ядра, их удаление заставит качать заново
```

Точный список снять с реальной установки Python-версии, а не по памяти.

Что при этом обязано сохраниться: `%LOCALAPPDATA%\SCVPN\profiles.json`,
`settings.json` и внутри него — `hwid`. Это отдельный пункт приёмки.

### 11.4. ARM без отдельного этапа

`docs/windows-arm64-plan.md` после этого порта устаревает наполовину:

| Из ARM-плана | Судьба |
|---|---|
| Этап 1, шаг 1 (`arch.py` через `IsWow64Process2`) | не нужен, `RuntimeInformation.OSArchitecture` |
| Этап 1, шаг 2 (ассеты по архитектуре) | переезжает в `CoreDownloader.cs` (8.6) |
| Этап 1, шаг 3 (метка `bin/arch.txt`) | переезжает туда же |
| Этап 1, шаг 4 (`x64compatible`) | переезжает в 11.2 |
| Этап 2 целиком (нативная arm64-сборка) | **исчезает**: `dotnet publish -r win-arm64` и всё |
| Этап 2, замена OpenCV | **исчезает**: OpenCV не будет с самого начала |
| Шаг 0 (проверка wintun на ARM) | **остаётся и обязателен** |

Единственная неизвестная из ARM-плана, которую C# не снимает, — встанет ли
драйвер wintun на arm64-ядре. Проверить это стоит прямо на этапе 0, вместе с
другими спайками: если arm64-wintun не заработает, это меняет тексты ошибок в
UI, а не архитектуру порта.

Второе следствие: паритет по архитектурам достигается бесплатно, поэтому
**обе сборки выпускаются с самого первого релиза** C#-версии — отдельного
«этапа ARM» больше нет.

## 12. Этап 6 — приёмка и удаление Python-версии

### Критерии приёмки

Функциональные (проверять на живой машине, не в тестах):

1. Установка поверх существующей Python-версии: профили на месте, `hwid` в
   `settings.json` не изменился, мусор PyInstaller из `{app}` исчез.
2. Чистая установка: первый запуск, «Скачать ядро Xray», добавление подписки,
   подключение.
3. Режим системного прокси: интернет идёт, при отключении прежние настройки
   прокси возвращаются.
4. TUN-режим: запрос UAC, адаптер `SCVPNTun` поднялся, трафик идёт, при
   отключении маршруты вернулись.
5. Раздельное туннелирование в обе стороны (только выбранные / кроме выбранных).
6. Приложение снято из диспетчера задач — оба ядра умерли вместе с ним,
   интернет остался работать.
7. Автоподбор отпечатка находит рабочий; замер пинга даёт числа того же порядка,
   что Python-версия на тех же серверах.
8. Сканер QR читает код с экрана телефона.
9. Все пункты меню «⋯» из `desktop/Windows/README.md` на месте и работают.
10. Всё перечисленное — на x64-машине и на ARM-машине.

Нефункциональные:

11. Запуск окна заметно быстрее нынешнего (у PySide6 холодный старт около
    двух секунд, у WPF — доли секунды). Если это не так, стоит разобраться:
    скорее всего дело в `PublishReadyToRun`.
12. Потребление памяти в простое не больше нынешнего.

### Удаление Python-версии

Только после пункта 10. Порядок:

1. снять эталонные файлы для тестов (раздел 13.2), если ещё не сняты, — **это
   последняя возможность**;
2. `git rm -r desktop/Windows`;
3. `git mv desktop/Windows-cs desktop/Windows`;
4. обновить `README.md` в корне и `desktop/Windows/README.md`: структура файлов,
   команды сборки, требования (Visual Studio / .NET SDK вместо Python);
5. `docs/windows-arm64-plan.md` — либо удалить, либо оставить с пометкой в
   шапке «устарел, см. windows-csharp-plan.md»; шаг 0 про wintun из него
   перенести сюда, если к тому моменту он ещё не выполнен.

## 13. Тесты

### 13.1. Что покрываем

Проект `SCVPN.Tests` (xUnit). Не «покрытие ради покрытия» — только места, где
ошибка **тихая**, то есть проявляется не падением, а неверным поведением:

* разбор ссылок всех четырёх протоколов, включая base64-подписки;
* сборка конфига Xray во всех режимах маршрутизации и с блокировкой рекламы;
* сборка конфига sing-box во всех трёх режимах раздельного туннеля;
* разбор заголовков подписки (трафик, срок, base64-имя);
* чтение и запись `profiles.json` / `settings.json` с сохранением неизвестных
  ключей;
* HWID на подставленном `MachineGuid`;
* выбор ассетов по архитектуре;
* сверка палитры с `android/.../colors.xml` (см. 9.1).

Не покрываем модульными тестами: UI, живую сеть, драйвер. Для них — приёмка
из раздела 12 и сквозная проверка из 13.3.

### 13.2. Эталонные файлы — снять до удаления Python

Самая дешёвая страховка во всём плане и единственный её срок — пока
Python-версия ещё работает.

Написать разовый скрипт в `desktop/Windows/`, который прогоняет через нынешний
код набор входных данных и сохраняет результаты в
`desktop/Windows-cs/SCVPN.Tests/Golden/`:

* 15–20 ссылок всех протоколов (взять из реальной подписки, обезличив
  UUID и пароли) → разобранные `Server` в JSON;
* по каждому серверу — готовый конфиг Xray во всех режимах;
* конфиги sing-box для трёх режимов раздельного туннеля;
* HWID от нескольких подставленных `MachineGuid`;
* реальный `profiles.json` (обезличенный) — как есть.

Дальше тесты C# сравнивают свой результат с этими файлами. Сравнивать
**разобранные JSON-документы**, а не строки: порядок ключей у `System.Text.Json`
и у Python не совпадает, и посимвольное сравнение утонет в ложных отказах.

Обезличивание обязательно — файлы лягут в git.

### 13.3. Сквозная проверка

Перевод `smoke_test.py` в консольный проект `SCVPN.Smoke` (или тест xUnit с
атрибутом-фильтром, чтобы не запускался в CI): те же пять шагов — импорт,
профили, конфиг Xray, `sing-box check`, реальный туннель с выходным IP. Нулевым
шагом печатать архитектуру ОС, архитектуру процесса и содержимое `bin/arch.txt`.

## 14. Что делаем не так, как в Python (и почему)

Список осознанных отступлений от паритета. Всё, чего в нём нет, переносится
как есть.

1. **Уборка осиротевших ядер** — job-объект вместо pid-файлов и `tasklist`
   (см. 0.3). Проблема закрывается ядром ОС, а не нашим кодом при следующем
   старте. Чтение старых pid-файлов остаётся временно, ради миграции.
2. **Список процессов** — `Process.GetProcesses()` вместо разбора вывода
   `tasklist` в кодировке cp866.
3. **Определение архитектуры** — одно свойство BCL вместо модуля с ctypes.
4. **Запись настроек** — атомарная. Нынешняя может потерять `hwid` при
   выключении питания.
5. **Системный прокси** — сохраняем и возвращаем прежнее значение
   пользователя, а не просто гасим флаг.
6. **Анимации** — средствами WPF, без таймеров с фиксированным FPS.
7. **Версия приложения** — одна, в `Directory.Build.props`, а не две.
8. **QR-код** — `QRCoder` даёт только матрицу, рисуем сами. Как и сейчас.

## 15. Риски

### 15.1. Отрисовка `PowerButton` не совпадёт с Qt

Вероятность высокая, ущерб низкий. Радиальный градиент, толщины колец и
сглаживание в WPF и Qt считаются по-разному, «попиксельно так же» не выйдет.
Мера: снять скриншоты всех состояний нынешней версии до удаления и сверять
глазами рядом. Отклонения в полпикселя допустимы, разъехавшийся диаметр — нет.

### 15.2. Кросс-сборка x64 с arm64-хоста

Вероятность средняя, ущерб средний. Снимается спайком 0.1. Запасной путь —
собирать x64 в GitHub Actions на `windows-latest`, это полчаса работы.

### 15.3. Камера

Вероятность средняя, ущерб низкий. Снимается спайком 0.2. Если оба пути
окажутся негодными: сканер QR — единственная функция, потеря которой не ломает
ни один режим работы (ссылку вставляют текстом). Тогда кнопка скрывается, а в
приёмке пункт 8 снимается — но решать это по результату замера, а не заранее.

### 15.4. Wintun на ARM

Вероятность низкая, ущерб высокий (TUN-режим на ARM не поднимется вовсе).
Единственная неизвестная, унаследованная из ARM-плана. Проверять на этапе 0.

### 15.5. SmartScreen

Неподписанный `.exe` даёт предупреждение при первом запуске. Так и сейчас, то
есть не регресс, но при смене исполняемого файла репутация обнулится в любом
случае. Если планируется подпись — сейчас удачный момент, потому что
подписывать заодно придётся и установщик. Отдельный вопрос, в план не заложен.

### 15.6. Потеря эталона

Как только Python-версия удалена, сверять поведение станет не с чем. Отсюда
жёсткое правило раздела 13.2: эталонные файлы снимаются **до** удаления, а сам
момент удаления — отдельный пункт после полной приёмки, а не «заодно с
последним коммитом».

## 16. Чего не делаем

* **MSIX и Microsoft Store** — приложению нужны права администратора и драйвер
  режима ядра, магазину оно не подходит.
* **Единый установщик с обеими архитектурами** — лишние 60 МБ ради экономии
  одного клика на странице загрузки.
* **Трей и автозапуск** — их нет в нынешней версии, паритет означает паритет.
  Как отдельная задача после порта — сколько угодно.
* **Автообновление приложения** — то же самое.
* **Защита от второго запуска** — её нет и сейчас; добавлять посреди порта
  значит менять поведение и объём приёмки одновременно.
* **Общий C#-код с другими платформами** — на macOS Swift, на Android Kotlin.
  Ещё один «общий слой» никто не будет поддерживать.
* **32-битный ARM** — как и в ARM-плане, не поддерживаем.

### Что проверено на этой машине (macOS)

Целевой фреймворк Windows-only, поэтому проверялось всё, что можно было
проверить локальным SDK:

1. **`Core/` и `Native/` компилируются** под C# 11 без единого предупреждения
   (отдельный проект на `net7.0`, куда включены только эти два слоя).
2. **82 теста проходят**, из них эталонных сравнений — большинство: 22 ссылки
   всех четырёх протоколов, 24 конфига Xray, 5 конфигов sing-box, 6 наборов
   заголовков подписки, HWID, круг чтение-запись профилей и настроек.
3. **Эталоны сняты с двух реализаций сразу.** Кроме Python-версии, тот же
   набор случаев прогнан через `core-swift` — отдельным дампером на Swift.
   Результат: конфиги Xray у Python и Swift совпали побайтно на всех 24
   случаях, подписи и разбор заголовков — тоже. Разошлись ровно три случая
   разбора ссылок, и все три — ошибки Python, которые Swift уже чинит
   (см. `SCVPN.Tests/Golden/README.md`). C#-парсер повторяет Swift.
4. **Вызовы QRCoder и ZXing.Net проверены живьём** — оба пакета
   кроссплатформенные, так что реальные вызовы из кода скомпилированы и
   запущены здесь же.

### Что не проверено

Всё, что связано с WPF: разметка XAML, самодельные элементы, окна. На macOS
это не собирается вовсе. Вместо компилятора работала вычитка отдельными
проходами — по XAML-именам, обработчикам событий, ключам ресурсов и типам
в `{x:Static}`, — но заменой сборке она не является. Первая сборка на Windows
почти наверняка даст ошибки, и это ожидаемо.

### Отступления от плана, сделанные по ходу

1. **Установщик больше не кладёт `bin/`.** В прежней версии он бандлил ядра со
   сборочной машины. Теперь ядра зависят от архитектуры, а сборочная машина —
   arm64: положить её `bin` в x64-установщик значило бы выдать заведомо
   нерабочие бинарники. Приложение скачивает их само при первом запуске (оно
   и раньше это умело), а метка `bin/arch.txt` не даёт перепутать архитектуру.
   Для существующих x64-пользователей ничего не меняется: их `bin` без метки
   считается x64 и заново не качается.
2. **`SelfContained` не в csproj, а в `build.ps1`.** В csproj это свойство без
   `RuntimeIdentifier` — ошибка сборки (NETSDK1031), и обычные `dotnet run` и
   `dotnet test` перестали бы работать.
3. **Пакетов NuGet два, а не три.** `CommunityToolkit.Mvvm` не понадобился:
   интерфейс переносился как есть, императивным кодом в code-behind, как это
   было в Qt-версии. Привязки нужны ровно в одном месте — списке серверов.
4. **Сквозная проверка — не отдельный консольный проект**, а тесты с
   `[Trait("Category", "Live")]` и выключателем `SCVPN_LIVE=1`. Отдельный
   проект дал бы то же самое ценой лишнего csproj в решении.
5. **Модуля `arch.py` нет вовсе.** `RuntimeInformation.OSArchitecture` в .NET
   уже возвращает архитектуру системы, а не процесса, — как и предполагалось
   в разделе 5.

### Что нашла вычитка

Отдельными проходами вычитывалось то, что нельзя проверить ни компилятором,
ни эталоном: сеть, процессы, реестр, разметка. Найденное чинилось на месте.
Самое существенное — чтобы было видно, чего стоила эта работа:

1. **Гонка в `XrayRunner`.** Событие `Exited` подписывалось до `Start()`, а
   ссылка на процесс присваивалась после. Ядро с битым конфигом умирает за
   десятки миллисекунд — и успевало доложить о смерти раньше, чем его
   записали. Доклад уходил в никуда, `StateChanged(false)` не приходил, и
   окно навсегда оставалось «подключено» к мёртвому ядру. Заменено на
   поток-ожидатель, как в `Tun` и в `core-swift`.
2. **Метка `bin/arch.txt` ручалась за файлы, которых загрузка не касалась.**
   На обновлении x64 → arm64 скачивание одного только ядра проставляло метку
   `arm64`, и оставшиеся x64-шные `sing-box.exe` с `wintun.dll` проходили
   проверку — приложение никогда бы не предложило их обновить.
3. **`wintun.dll` не перекачивался никогда**, если файл уже лежал на диске, —
   ровно тот случай, который ARM-план называл самой коварной ошибкой: DLL
   чужой архитектуры в процесс sing-box не загружается вовсе.
4. **Бегущая полоса загрузки роняла приложение.** Анимация целилась в
   безымянный `LinearGradientBrush` внутри `ControlTemplate`, а такие WPF
   замораживает — первое же скачивание файла с неизвестным размером давало
   исключение.
5. **Кнопка «Отмена» в окне загрузки была мёртвой** — событие было, токен
   отмены не передавался.
6. **Шаблон строки списка серверов не написал никто.** Оба файла ссылались
   друг на друга; список показал бы `SCVPN.Controls.ServerRow` вместо строк.
7. **`FreePort.Find(0)` возвращал ноль** — ядро подняло бы вход на случайном
   порту, а приложение ходило бы на нулевой. Значение приходит из
   `settings.json`, который правят руками.
