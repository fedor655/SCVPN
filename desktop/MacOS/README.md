# SCVPN для macOS

Клиент-обёртка вокруг открытого ядра [Xray-core](https://github.com/XTLS/Xray-core).
Общее описание проекта и разбор архитектуры — в [README репозитория](../../README.md).

Только Apple Silicon. Общий код лежит в `../shared/`, здесь — то, чем macOS
отличается.

## Запуск из исходников

venv для этого проекта нельзя ставить внутри `desktop/MacOS` (и вообще внутри
`~/Documents`): эта папка синхронизируется iCloud Drive, а синхронизация
метит файлы внутри `venv/` флагом `UF_HIDDEN` — не всё дерево репозитория
разом, а только то, что внутри `venv/`, но зато постоянно и по кругу (после
чистки флаг возвращается за 75–90 секунд). Файлы под этим флагом Qt не видит,
включая собственные плагины платформы (`libqcocoa.dylib` и соседей), и
приложение падает ещё до создания окна — без единой подсказки почему, если не
знать про эту особенность заранее. Поэтому venv живёт вне репозитория, в
`~/.venvs/scvpn` (переопределяется переменной `SCVPN_VENV`); `run.py`,
`test.sh` и `build.sh` рассчитаны именно на такое расположение.

```bash
# зависимости (один раз)
python3 -m venv ~/.venvs/scvpn
~/.venvs/scvpn/bin/pip install -r requirements.txt

# запуск
~/.venvs/scvpn/bin/python run.py
```

При первом запуске: меню **«⋯» → «Скачать ядро Xray»**, затем кнопка **+** —
вставь `vless://…` ссылку или URL подписки, выбери сервер и жми большую кнопку.

## Интерфейс

Экран — кнопка подключения, статус и список серверов. Всё остальное в меню «⋯»:

| Пункт | Что делает |
|---|---|
| Способ подключения | системный прокси или TUN (весь трафик, нужен root) |
| Отпечаток TLS | авто-подбор или конкретный |
| Сетевой стек TUN | gvisor / system / mixed — крутить, если туннель странно себя ведёт |
| Включать системный прокси | только для режима «прокси» |
| Блокировать рекламу | правило в конфиге Xray |
| Раздельное туннелирование… | маршрутизация целиком: всё через VPN, обход, или какие приложения идут в туннель (нужен TUN) |
| Подписки… | список подписок, ссылка, QR-код, удаление подписки целиком |
| Измерить пинг | TCP-пинг всех серверов |
| Скачать ядро Xray | разовая загрузка ядра и гео-баз |
| Скачать компоненты TUN | попросить системный компонент скачать `sing-box` |
| Удалить системный компонент… | снять привилегированный демон |
| Показывать лог ядра | панель с выводом Xray внизу окна |

Удалить сервер — правой кнопкой по строке или `Delete`.

## Режимы

- ✅ **Системный прокси** — без пароля: `networksetup` доступен администратору
  напрямую. Покрывает браузеры и приложения с интерфейсом; консольные утилиты
  про эту настройку не знают.
- ✅ **TUN — весь трафик**: Xray делает соединение с сервером, а `sing-box`
  заворачивает в него весь трафик системы через utun-адаптер.

## Как устроен TUN и почему так

TUN требует root. Пароль спрашивается **один раз** — при установке системного
компонента; дальше приложение говорит с ним по `/var/run/scvpn-helper.sock`.

Компонент — это LaunchDaemon `com.scvpn.helper`. Он поднимает sing-box, следит
за ним и, главное, следит за соединением с приложением: обрыв соединения
означает, что приложение мертво, и демон снимает туннель сам. Без этого
падение приложения оставило бы root-овый sing-box держать маршруты, а весь
трафик системы — уходить в мёртвый туннель; снять его было бы некому.

Границы, которые компонент держит:

- сокет открыт только группе `admin`, права `0660`;
- готовый конфиг он не принимает — только параметры, каждый проверяется
  (`helper/config.py`), конфиг собирает сам;
- запускает только бинарники из `/Library/Application Support/SCVPN/bin`,
  принадлежащие root и недоступные на запись остальным. Поэтому `sing-box`
  (SagerNet, официальный GitHub-релиз) скачивает туда сам демон, а не
  приложение.

Снять компонент: меню «⋯» → «Удалить системный компонент…». Руками:

```bash
sudo launchctl bootout system/com.scvpn.helper
sudo rm -f /Library/LaunchDaemons/com.scvpn.helper.plist
sudo rm -rf "/Library/Application Support/SCVPN"
sudo rm -f /var/run/scvpn-helper.sock
```

Лог демона — `/var/log/scvpn-helper.log`.

## Структура

| Файл | За что отвечает |

| `../shared/` | общий с Windows код: парсеры, модели, конфиг Xray, хранилище, интерфейс |

| `native/apps.py` | список запущенных приложений для раздельного туннелирования |
| `helper/config.py` | конфиг sing-box и валидация недоверенного ввода |
| `helper/daemon.py` | сам демон: сокет, надзор за sing-box, установка sing-box |

| `setup/scvpn.icns` | иконка, нарисована один раз (см. `setup/README.md`) |

## Проверка

```bash
./test.sh            # модульные проверки платформенного слоя
./test.sh smoke      # живая проверка: парсинг, конфиги, туннель
./test.sh мой.py     # свой скрипт в окружении проекта
```

Проверка `test_snapshot_round_trip_restores_state` реально включает и выключает
системный прокси на этой машине — так и задумано: молча сломанный откат
оставляет без интернета, и ловить это надо здесь.

### Ручная проверка TUN и dead-man's switch

Модульные проверки не поднимают настоящий демон (установка требует пароль
администратора). Живьём это нужно проверить руками — одной непрерывной
последовательностью, а не разрозненными шагами: `MainWindow.__init__` зовёт
`cleanup_stray()`, который бьёт по `data/xray.pid`, и второй запущенный
экземпляр застрелил бы ядро первого.

Делать это на машине, где потерять сеть на пару минут не страшно, и **не по
SSH-сессии в эту же машину** — провальный исход последнего шага означает, что
весь трафик заперт в мёртвом туннеле, а приложение, которое могло бы его
снять, уже убито `-9`.

```bash
cd desktop/MacOS

# --- Установка venv (один раз, если ещё не стоит) ------------------------
python3 -m venv ~/.venvs/scvpn && ~/.venvs/scvpn/bin/pip install -r requirements.txt

# --- Шаг 1: запуск, режим "прокси" ---------------------------------------
~/.venvs/scvpn/bin/python run.py &
APP_PID=$!
#   - меню «⋯» показывает «Сетевой стек TUN» (gvisor/system/mixed) и
#     «Удалить системный компонент…» сразу под «Скачать компоненты TUN»
#   - подключиться в режиме прокси, проверить: networksetup -getwebproxy Wi-Fi
#     (Server 127.0.0.1), отключиться, проверить Enabled: No

# --- Шаг 2: переключиться на TUN В ЭТОМ ЖЕ окне ---------------------------
# НЕ закрывай окно из шага 1 и НЕ запускай второй экземпляр — см. предупреждение
# про cleanup_stray() выше. Один и тот же APP_PID до самого конца проверки.
# В меню «⋯» → «Способ подключения» → TUN, подключиться. Первое подключение
# спросит пароль администратора на установку демона — это ожидаемо.

# --- Шаг 3: зафиксировать, что туннель ДЕЙСТВИТЕЛЬНО поднят ---------------
# ifconfig ниже НЕ доказательство сам по себе: на типичной машине уже стоят
# посторонние utun0..utun9 (Tailscale и т.п.), grep будет зелёным всегда,
# даже если наш туннель не поднялся. Доказательство — непустой SB_PID.
SB_PID=$(pgrep -f "sing-box run -c")
[ -n "$SB_PID" ] || { echo "СТОП: sing-box не поднялся, дальше идти нельзя"; exit 1; }
HELPER_PID=$(pgrep -f "run.py --helper")   # верно только для запуска из исходников;
                                            # в собранном .app командная строка
                                            # демона другая, без "run.py"
[ -n "$HELPER_PID" ] || { echo "СТОП: демон не найден"; exit 1; }
ifconfig | grep -A3 utun                   # адаптер есть — но см. оговорку выше
curl -s -m 10 https://api.ipify.org        # адрес сервера, а не свой

# --- Шаг 4: главное — dead-man's switch (то, ради чего эта архитектура) --
kill -9 "$APP_PID"                   # снят ТОЛЬКО процесс приложения
sleep 12                             # >= STOP_GRACE_SEC(7)+KILL_GRACE_SEC(3)=10, с запасом

# Демон обязан остаться ТЕМ ЖЕ процессом — не просто "что-то нашлось", а
# именно тот же PID. Если PID сменился — демон тоже погиб, и его поднял
# заново launchd (KeepAlive); новый демон на старте сам зовёт
# kill_stale_singbox() и подметает осиротевший sing-box — все проверки ниже
# позеленеют даже при полностью сломанном обнаружении обрыва клиента.
NEW_HELPER_PID=$(pgrep -f "run.py --helper")
[ "$NEW_HELPER_PID" = "$HELPER_PID" ] || { echo "СТОП: демон перезапустился (было $HELPER_PID, стало $NEW_HELPER_PID) — проверка ничего не доказывает"; exit 1; }

# sing-box с тем PID, что засекли на шаге 3, обязан исчезнуть — не просто
# "sing-box не видно вообще", а именно ЭТОТ процесс:
kill -0 "$SB_PID" 2>/dev/null && echo "ПРОВАЛ: sing-box $SB_PID пережил обрыв клиента" || echo "OK: sing-box снят"
pgrep -fl sing-box                   # для общей картины — тоже должно быть пусто

# Прямая улика вместо косвенного отсутствия процесса:
grep "клиент отключился, а туннель поднят — снимаю его" /var/log/scvpn-helper.log | tail -1

curl -s -m 10 https://api.ipify.org  # интернет на месте, адрес свой

# xray-ядро (не sing-box) сиротеет отдельно — у него нет своего демона-
# надзирателя, только cleanup_stray() при следующем запуске приложения.
# Это ОЖИДАЕМО, не поломка — непустой результат здесь в порядке вещей:
pgrep -fl xray

# --- Если шаг 4 провалился и трафик заперт в туннеле: откат --------------
sudo pkill -f 'sing-box run -c'
#   мягче — новый демон подметёт сироту сам:
sudo launchctl kickstart -k system/com.scvpn.helper
sleep 3                                  # демон поднялся и подмел синг-бокс
#   крайний случай — снять демон целиком через приложение (нужен новый
#   запуск, старый уже убит на шаге 4): меню «⋯» → «Удалить системный
#   компонент…»
#
# Проверка, что откат сработал:
curl -s -m 10 https://api.ipify.org      # интернет вернулся
pgrep -fl sing-box                       # осиротевших синг-боксов нет

# --- Шаг 5: раздельное туннелирование --------------------------------------
# Старый экземпляр уже мёртв после шага 4 — новый запуск безопасен, второй
# активный экземпляр не образуется.
~/.venvs/scvpn/bin/python run.py
#   Режим «только выбранные через VPN», один браузер, подключиться;
#   в браузере — серверный адрес, в curl из терминала — свой.
#   Если process_name-правила sing-box на darwin не сработают —
#   пометить в этом README как неподдерживаемое и отключить
#   пункт меню на macOS вместо тихой поломки.
```

## Сборка

```bash
./build.sh           # dist/SCVPN.app
```

Сборка тоже не может жить внутри репозитория — та же причина, что и у venv:
`~/Documents` синхронизируется iCloud Drive, и рано или поздно (по замерам —
за 75–90 секунд) синхронизация начнёт метить часть из сотен файлов бандла
флагом `UF_HIDDEN`, и приложение сломается тем же способом. Поэтому
PyInstaller собирает во временный каталог `~/.scvpn-build`
(переопределяется `SCVPN_BUILD_DIR`), а `desktop/MacOS/dist` и `desktop/MacOS/build`
— лишь симлинки на него; путь `dist/SCVPN.app` остаётся тем же, но сами байты
бандла никогда не попадают под синхронизацию.

Приложение подписано ad-hoc, без Apple Developer ID, поэтому первый запуск —
через ПКМ → «Открыть». Иконка при сборке не генерируется: `setup/scvpn.icns`
лежит в git готовым — как его перерисовать, см. `setup/README.md`.

## Где лежат данные

В режиме разработки всё открыто в папках `data/` и `bin/` рядом с проектом;
в собранном приложении — в `~/Library/Application Support/SCVPN`:

- `profiles.json` — подписки и серверы;
- `settings.json` — настройки;
- `xray_running.json` — конфиг, реально отданный ядру;
- `sysproxy_backup.json` — что стояло в системном прокси до нас;
- `bin/` — ядро Xray и гео-базы.

`sing-box` лежит отдельно, в `/Library/Application Support/SCVPN/bin`: его
запускает root, и писать туда пользователь не должен.
